# 素材属性与交付契约

> **Windows 版边界（先读）**：本 Skill 的 Windows 版**只交付剪映原生草稿**。
> 下文凡是“交付 Final Cut XML / FCPXML / both”的分支均为 macOS 原版语义，
> 在 Windows 宿主上**禁用**——用户要求时停下说明本版不支持，不得尝试生成 FCPXML
> （`p4f_*` / `finalize_fcp` 代码保留仅作对照）。剪映相关的规则全部照常生效。

## 原素材进入

先用 `p0_建工作区.py` 和 `ffprobe` 读取显示画幅、编码画幅、旋转、真实帧率、音频采样率与声道。不得用 1080p、60fps 或横屏作为默认值。

- 新建 Final Cut 或剪映项目时，项目显示画幅与帧率必须等于原素材。
- Final Cut XML 只引用原文件。剪映草稿优先直接引用稳定原文件；原片在 Downloads、Desktop、Documents、临时附件目录、移动硬盘或网络卷时，默认建立受管副本（macOS 用 APFS clone 写时复制，Windows 用普通复制），复制后校验 SHA-256。两种分支都不转码、不缩放、不裁切、不烘焙旋转、不重采样音频，也不移动或删除原片。
- 4K 保持 4K，1080p 保持 1080p；`60000/1001` 不能写成 60。
- 多素材属性不一致时停止，请用户指定主项目标准；不能自动统一。
- 内部词轴可以使用稳定分析网格，但最终工程必须量化回原素材真实帧网格。

多素材还必须先判断入口成熟度：原始多文件直接交给 AI 粗剪时，当前主链尚未完成
“素材集锁→逐源词轴→跨源选材/排序→逐源独立声学验收→多 asset 终版”的闭环，
因此只探测并停止。用户交来多素材人工粗剪 XML，或已有通过验收的 source-aware
`rough_segments.json` 时，允许从相应冻结点继续；每段必须携带 `source_id`，下游逐段
反查对应原文件。不得因为 `p2c/p4j` 已能写多素材工程，就反推 P0/P1 已经支持。

以上是“从原素材新建工程”的规则。若输入是用户已经完成的人工粗剪 XML，且用户要求只加字幕，则以“不改人工 XML”为更高优先级：保留它现有的项目 format 与全部工程属性，即使项目时间线与源文件帧率并不相同，也只报告、不擅自改写。

`media_contract.py` 是媒体属性探测与 Final Cut 字幕 profile 的代码真相源。剪映的字号、颜色、X/Y 和段内时码投影只在 `jianying_contract.py` 维护；两条交付分支不共用可变样式数值。

## 色彩元数据缺失

原素材的 primaries / transfer / matrix 三项明确且都为 bt709 时，Final Cut 直接使用 Rec.709。只要任一项缺失，就不得根据 H.264、10-bit、4:2:2、分辨率或文件名猜色彩。若有同一原素材的 Final Cut 实机导出 XML，可在 P0 使用 `--color-reference-xml`；契约必须绑定参考 XML 哈希、素材规范路径、大小、修改时间、时长、画幅、帧率和音频，生成与验收每次都重新解析参考。只借用 `format@colorSpace`，不继承参考工程帧率、format 或 `colorSpaceOverride`。任一指纹漂移即停止 Final Cut 交付；剪映原生草稿不声明此 FCPXML 字段，不被这一分支连带阻断。

## 交付分叉

**Windows 版只有第二条可用**（见文首边界声明）；第一条与 `both` 在 Windows 上禁用。

- （macOS 原版语义）用户明确说 Final Cut、FCPXML 或 XML：交付 Final Cut XML。
- 用户明确说剪映：只交付剪映原生草稿。兼容 XML 只在用户明确要“剪映 XML”时另行生成。
- 用户没有说明：默认剪映原生草稿。

默认剪映分支不设置用户粗剪审核环节。F1 只是内部声学验收与冻结；通过后连续完成字幕、平台封装、草稿终检和草稿箱登记。除非用户明确只要粗剪，不另外生成粗剪审核 XML，不暂停等待确认。

剪映的应用位置或数据位置可以被用户修改，因此不得用单一写死路径登记草稿。终结器必须用 `p4j_定位剪映草稿根.py --save` 选择当前草稿根，并验证 `root_meta_info.json` 是剪映已初始化、结构有效且可写的索引。多路径冲突时优先显式路径、运行中剪映和最近活动目录；仍无法唯一确定时停止，不在旧草稿箱制造“生成了但剪映看不见”的假交付。
定位器必须保留结构有效但当前进程不可写的候选，并报告 `current_process_write_denied`。这种情况是系统权限问题，不是剪映未初始化。
- 只有用户明确要求两份时才交付 `both`（macOS 原版语义；Windows 版禁用，停下说明）。

## 人工粗剪 XML：只加字幕

用户说明粗剪已由人工完成，并交来 XML 要求加字幕时，该 XML 本身就是冻结基准，跳过 AI 粗剪与确认循环：

1. 记录 XML 路径、SHA-256、项目 format 和完整节点结构。
2. 只读取 XML 已选片段对应的声音，做 ASR 修字、断句和字符级字幕对齐。
3. 用 `p2d_回灌人工粗剪.py` 建字幕投影工作区；这里的 keep 只服务字幕识别，不获得改刀权限。
4. 用 `p4h_包装人工粗剪.py` 只添加 Basic Title 字幕与必要 effect 资源。
5. 生成后移除新增字幕再做全结构指纹；必须与输入 XML 一致。

禁止改项目名、UID、modDate、format、素材资源、marker、clip 数量、顺序、`ref`、`offset`、`start`、`duration`、音频、变速、转场、缩放或旋转。发现半词、错刀或属性冲突时只报告；未经用户授权不得修剪。

人工 XML 输入属于显式 XML 场景，默认仍交付“加字幕后的 Final Cut XML”（macOS 原版语义；Windows 版禁用该交付分支——用户交来 FCPXML 要求只加字幕时停下说明本版不支持，人工 XML 路线在 Windows 上暂不可用），不套用“未说明则剪映”的原素材默认分支。

该入口等同于固定流程中的 F1 已完成：继续执行 P2 字幕文字 → P3 声学对齐 → P4 当前画幅基础字幕样式 → P6 Final Cut 交付，明确跳过 P1 和 P5。文字、对齐、样式分别修正，不能用“只加字幕”把三层混成一次整体改动。

## 人工粗剪 XML：继续包装

用户明确说“在这个人工粗剪上继续包装”时，权限与“只加字幕”不同：跳过 AI 粗剪，但允许在冻结口播上新增包装层。

1. 记录输入 XML 路径、SHA-256、项目属性、原素材和口播音频覆盖。
2. 先完成基础字幕真值，再读取素材类型对应的 `子技能/包装/` 文件。
3. 允许新增标题、音乐/音效、调整层、局部画面处理和转场；不得重选内容。
4. 为画面效果拆分或容器化视频时，口播音频的来源、范围、顺序和连续性必须保持。
5. 分别验收技术属性、核心对白、字幕真值、包装文字、画面结构、混音与平台格式。

执行顺序仍是 P2 → P3 → P4 → P5 → P6；获得 P5 权限不等于可以重做 P2/P3/P4。

如果用户没有明确把权限从“只加字幕”扩大到“继续包装”，仍执行上一节的严格全结构指纹。若用户反馈切口并要求改内容，退回粗剪，而不是在包装分支修刀。

## 字幕画幅

- 1080×1920 与 1920×1080 分别使用用户确认的竖屏、横屏 profile。
- 3840×2160 Final Cut 基础字幕使用用户实机确认的 120 / X=0 / Y=-478.53，不按 1920×1080 的像素倍数放大。
- 2160×3840 Final Cut 基础字幕使用聚珍体 52 / X=0 / Y=-190，投影为黑色、75% 不透明度、0.63 模糊、距离 2、角度 315°。这是 Final Cut 实机校准值，不向其他画幅扩散。
- 任何没有用户实机确认值的精确画幅都不能作为正式交付，不能静默套用或推算。
- 剪映原生草稿使用剪映原生字号与字体资源，不复制 Final Cut 的像素坐标。已确认 1080×1920 为聚珍体 14 / X=0 / UI Y=-728 / 首次载入 `transform.y=-0.3791667` / 纯白；2160×3840 也已由用户在剪映实机确认，使用聚珍体 14 / X=0 / `transform.y=-0.3791667` / 纯白；3840×2160 剪映样式单独登记。三者都是独立登记的精确画幅 profile，不从 Final Cut 参数或其他分辨率临时推导。

## 技术验收

Final Cut XML、剪映 XML 与剪映草稿都必须反查真实素材，核对画幅、帧率、素材路径、音频属性、主轨连续性和字幕覆盖；XML 还必须通过对应 FCPXML DTD。技术通过不等于用户视觉验收。

多素材剪映草稿还必须逐项验收：项目素材库的原文件集等于冻结粗剪实际引用集；每份原素材只登记一次；每个主轨片段的 `material_id` 按 `source_id` 对应正确原文件；每段原素材入出点和时间线位置与冻结粗剪逐段一致。每张字幕必须归属唯一视频段，按该段 target 起点加段内声学偏移生成；验收器逐张禁止越过视频切点。

剪映验收分三层：

1. `complete_structural`：JSON、素材路径/哈希、主轨、字幕与素材声明通过；
2. `relink_required / material_bin_failed`：结构已生成，但剪映实机还不可用；
3. `complete_runtime_verified`：项目素材可见、时间线无权限错误、播放器能出画面，且已写入实机证据。

`run_manifest_jianying.json.complete` 只能在第 3 层为 `true`。静态 JSON 验收不得自行填写剪映界面或运行时结果。

第 2 层不是默认终点。发现“链接媒体/无访问权限”或项目素材为空时，先从 `media_delivery.json` 读取当前草稿的 `delivery_path`，再通过剪映自己的链接或导入界面选择该文件。macOS 上这一界面动作同时让剪映获得系统的正式文件授权；Windows 上无此机制，走剪映“重新链接/导入”对话框即可。禁止伪造授权信息或只改 JSON。修复后重新执行三项实机验收；当前宿主无法操作剪映界面时，才将“按精确路径链接一次媒体”作为唯一用户待办。

# 固定工序与问题归属

## 唯一顺序

```text
P0 技术属性
→ R 素材类型路由
→ P1 对应类型粗剪
→ F1 内部声学验收/冻结
→ P2 字幕文字与断句
→ P3 字幕声学对齐
→ P4 基础字幕样式
→ P5 其他包装
→ P6 平台交付
```

前一工序没有完成，后一工序不得开始。P1 通过 F1 后成为后续工序的只读输入；正常流程不等待用户确认粗剪。发现问题先归属，不允许用下游效果遮盖上游错误。

## 工序所有权

| 工序 | 只负责 | 主要产物/真相源 | 出错时允许修改 | 绝对不能顺手修改 |
|---|---|---|---|---|
| P0 技术属性 | 原素材画幅、帧率、旋转、音频、交付平台 | `config.json`、`media_contract.py` | 技术探测与项目声明 | 内容、字幕、包装 |
| R 素材路由 | 识别单人口播、学员好评、双人口播等内容关系 | `material_type`、`material-routing.md` | 类型判断与子技能选择 | 用一个类型规则替代另一个类型 |
| P1 粗剪 | 选材、删留、顺序、开头、刀口、尾音 | `content_plan/keep/expression_review/structure/rough_segments/cut_review` | 对应素材类型的粗剪方法、边界和结构 | 字幕样式、音乐、工程载体 |
| F1 冻结 | 独立音频验收后把粗剪变成只读上游 | `p1b`、`decision_lock.json` 或人工 XML 哈希 | P1 重审后显式重建 | 未验收直接包装、静默覆盖锁 |
| P2 字幕文字 | ASR 修字、逐字真值、断句、语义关键词候选 | `cards.json`、`字幕分卡.md` | 文字、卡边界、候选词 | 粗剪几何、字幕时码、样式、最终上色 |
| P3 字幕对齐 | 每张既定卡何时出现和切换 | `captions_plan.json`、`p3_分卡.py`、`jianying_contract.project_card_timerange()` | 字符级时码、首卡吸附、受限 VAD、剪映段内投影 | 改字、重断句、字号/Y 轴 |
| P4 基础字幕样式 | 字体、字号、基础颜色、对齐、X/Y、投影、平台+画幅 profile | Final Cut `media_contract.caption_profile()`；剪映 `jianying_contract.caption_profile()` | 对应平台与精确画幅的基础样式 | 粗剪、文字、字幕时码、概念大字 |
| P5 其他包装 | 音乐、音效、概念大字、稀疏重点上色、批注、调整层、转场 | 对应素材类型包装子技能、剪映 `jianying_packaging.json`、Final Cut `final_cut_packaging.json` | 当前明确授权且已有实现的包装组件 | P1–P4 的任何真值 |
| P6 平台交付 | Final Cut/剪映结构、素材路径、DTD、命名 | `technical-delivery.md`、`p4f/p4j` | 平台序列化和工程结构 | 重新做内容或字幕判断 |

## 反馈路由

- “这段不该留、顺序不对、切得太紧、尾音没收住” → P1。
- “字错了、漏字了、这句话断得不自然” → P2。
- “文字是对的，但早了/晚了/视频先走一帧字幕才出现” → P3。
- “位置太高、字号不对、竖屏应该是这个 Y 轴” → P4。
- “每张都有颜色、重点太多或该强调的没强调” → P5（不回写 P2 keyword）。
- “音乐、音效、概念大字、画面效果不对” → P5。
- “XML 导不进、分辨率声明错、素材丢失、剪映不是真主轨” → P6。

一个反馈包含多类问题时，按 P0→P6 顺序分别处理。先修最早出错工序，重新生成下游后，再判断后面的反馈是否仍存在；不得把多个问题揉成一条模糊的“整体优化”规则。

用户精调 XML 属于交付后的 L 学习层：先生成分层差异，再把每一项路由回 P0–P6。L 不直接改时间线，也不允许一次反馈跨层重写全部规则。

## 修正纪律

修正上游会让下游产物失效，但不代表可以同时改下游规则。例如 P1 改刀后，P2–P6 需要按固定流程重新生成；在重新生成过程中仍沿用原规则，除非用户也明确指出对应工序的问题。

P2 修正错字时，现有工程可能需要把唯一修字结果回写词轴、`rough_segments.text` 和新的决策锁。此时只允许文字字段变化；源素材、`in_f/out_f`、播放顺序、词身份和刀口几何必须保持。`subtitle-text` 工序锁验证的正是这组几何不变量。重建锁只是更新派生哈希，不等于重新获得 P1 改刀权限。

每次修正先执行：

```bat
"%PY%" "%BASE%\脚本\stage_scope_guard.py" begin <工作目录> <scope> [--force]
```

完成后执行：

```bat
"%PY%" "%BASE%\脚本\stage_scope_guard.py" verify <工作目录>
```

`subtitle-text` 保护媒体和粗剪几何；`subtitle-alignment` 额外保护字幕文字；`subtitle-style` 再保护字幕时码；`packaging/delivery` 还保护已确认的基础字幕 profile。验证失败说明本轮越权修改了上游，必须撤回越权部分。

## 本轮竖屏样本的固定结论

C2900/C2901/C2903 这一个证据家族确认：

- 1080×1920 竖屏基础字幕使用 `XQjuzhentiZJSY`、字号 50、居中、X=0、Y=-220；
- 用户 17:57 成片 XML 的 274 个标题中，263 个仍严格使用这一基础 profile，其余是 P5 的开场命题、概念大字或编辑批注，不能混入 P4；
- 段首字幕和段内换卡是两套对齐问题：前者处理切口处 1–2 帧空档，后者服从下一卡首字起音；
- 这条样本确认的是阶段分离与竖屏基础 profile，不是固定大字、固定音乐或固定效果数量。

## 本轮 4K 横屏样本的固定结论

DSCF2925 的 Final Cut 实机截图确认 3840×2160 基础字幕为聚珍体、字号 120、居中、
X=0、Y=-478.53；这只修正 P4。随后同一成片的用户精调 XML 又提供了独立的 P1/P2
反馈：粗剪头尾与内容改动只更新 P1；横版长字幕的重切只更新 P2，且基础字幕保持单行，
当前横版字宽护栏为 13。两类反馈必须分别入档，不能因为来自同一 XML 就把 P1/P2/P4
合成“整体优化”。该证据否定“4K 字幕参数等比放大”，但不能推导 2160×3840 竖屏
或其他未确认画幅。

## 本轮剪映原生草稿的固定结论

- 1080×1920：聚珍体 14，X=0，剪映界面 Y=-728，首次载入草稿写 `transform.y=-0.3791667`，基础色纯白 `#FFFFFF`。实机确认换算为 `-728 / 1920`；交付前必须首次打开反查 UI，不能把像素值直接照抄进 JSON。
- 2160×3840：用户已人工确认聚珍体 14、X=0、`transform.y=-0.3791667`、基础色纯白 `#FFFFFF`。这是独立的剪映竖屏 4K profile，生产时直接使用，不再设置二次用户确认闸门，也不从 Final Cut 52/-190 或 1080p 像素值推导。
- 3840×2160：剪映原生字幕沿用当前实测 8，X=0，`transform.y=-0.72`，基础色纯白。不得用 Final Cut 的 120/-478.53 直接填入剪映 JSON。
- P2 的 keyword 只是候选；P5 另建显式重点清单，总密度不超过 6%。
- P6 字幕时码以归属视频片段为锚，禁止再用全片绝对换算积累误差。
